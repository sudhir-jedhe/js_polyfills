# Scenario: A Legacy Page's CSS Math "Doesn't Add Up"

**Scenario:** A legacy internal tool's page has a sidebar that's supposed to be exactly `250px` wide (`width: 250px; padding: 20px; border: 1px solid #ccc;` in the CSS), but visually it renders noticeably wider than that, and nudging padding/border values doesn't produce the expected pixel changes. Other pages in the same app render fine with identical CSS rules. What's the likely cause, and how do you confirm it?

**Diagnosis:** This is the signature symptom of **quirks mode**: in quirks mode, browsers use the old "quirks" box model where `width` includes padding and border (behaving as if `box-sizing: border-box` were forced), *and* the browser's other legacy layout emulations kick in — but only on this one page, meaning something is different about this specific document's parsing mode, not its CSS.

**Confirming it:**

```js
// run in the DevTools console on the broken page
console.log(document.compatMode);
// "BackCompat" -> confirmed: quirks mode
// "CSS1Compat" -> standards mode; the bug is something else
```

Checking "View Source," the page is missing `<!DOCTYPE html>` entirely — it was likely stripped by an old server-side templating include, or the page was generated by a legacy tool that never added one.

**Fix:**

```html
<!DOCTYPE html>  <!-- must be the literal first line/bytes of the document, nothing before it -->
<html lang="en">
<head>...
```

Adding this single line switches the page into standards mode, and the box model calculation immediately matches the CSS as written (`width` no longer silently absorbs padding/border). **Caution before shipping:** flipping quirks mode → standards mode is a page-wide change — anything else on the page that was accidentally relying on quirks-mode table-cell sizing or font-inheritance quirks can shift too, so a full visual regression pass on that page (not just the sidebar) is warranted, not just a narrow fix-and-ship of the one reported symptom.
