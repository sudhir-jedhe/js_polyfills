In JavaScript, top-level `let` and `const` declarations **do NOT become properties of the global object** (such as `window` or `globalThis`). Only top-level `var` and `function` declarations are attached to `window`.

```javascript
// Running at top-level in a browser script:
var x = 10;
let y = 20;
const z = 30;

console.log(window.x); // 10
console.log(window.y); // undefined
console.log(window.z); // undefined

// Yet y and z are still globally accessible:
console.log(y); // 20
console.log(z); // 30

```

---

### How the Engine Separates Them Under the Hood

When ES6 introduced `let` and `const`, the ECMAScript specification redesigned how the **Global Environment Record** stores variables. The global environment is split into two distinct sub-records:

```
┌──────────────────────────────────────────────────────────────┐
│                  Global Environment Record                   │
│                                                              │
│  1. Object Environment Record                                │
│     └─► Tied directly to the global object (`window`)        │
│     └─► Stores: `var`, `function` declarations               │
│                                                              │
│  2. Declarative Environment Record                           │
│     └─► An isolated, optimized internal engine record        │
│     └─► Stores: top-level `let`, `const`, `class`            │
└──────────────────────────────────────────────────────────────┘

```

When you reference a variable like `y`:

1. The engine checks the **Declarative Environment Record** first.
2. If not found, it falls back to checking the **Object Environment Record** (`window`).

---

### Why TC39 Designed It This Way

**1. Preventing Accidental Overwrites of Browser APIs**
The `window` object contains hundreds of built-in properties and methods (`name`, `length`, `location`, `open`, `status`, `history`).

With `var`, declaring `var name = "Alex"` accidentally overwrites `window.name` (which stringifies and overrides browser tab metadata). By placing `let` and `const` in the Declarative Environment Record, your variables never collide with or corrupt native `window` properties.

**2. Enforcing `const` Immutability**
Properties on the `window` object are standard object properties with configurable/writable descriptors. If `const` were placed on `window`, it could be mutated or deleted via object property assignment (`window.MY_CONST = 123` or `delete window.MY_CONST`), violating the immutability guarantee of `const`.

**3. Enforcing the Temporal Dead Zone (TDZ)**
`let` and `const` are hoisted in an **uninitialized** state (TDZ). If they lived directly on `window`, accessing `window.myLet` before its declaration would simply return `undefined` like any non-existent object property, breaking the strict TDZ error-handling rule.

**4. Performance and Compiler Optimization (V8 / JavaScriptCore)**
Accessing properties on the dynamic `window` object requires hash-map lookups and prototype chain traversal. Variables in the Declarative Environment Record can be stored in fixed, static memory offsets, allowing modern JIT compilers to optimize read and write speeds.

### Summary

| Declaration         | Stored In                      | Visible on `window`?              | Accessible Globally? |
| ------------------- | ------------------------------ | --------------------------------- | -------------------- |
| **`var`**           | Object Environment Record      | **Yes** (`window.x`)              | Yes                  |
| **`let` / `const**` | Declarative Environment Record | **No** (`window.y === undefined`) | Yes                  |
