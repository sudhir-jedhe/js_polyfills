Here is a comprehensive set of complex output scenarios involving `var`, `let`, and `const`. These questions highlight edge cases like the Temporal Dead Zone (TDZ), block scoping, hoisting, re-declaration, object freezing, and loop closures—frequently tested in senior JavaScript interviews.

---

### Scenario 1: The Temporal Dead Zone (TDZ) vs. Shadowing

```javascript
var x = 10;

function test() {
  console.log(x);
  let x = 20;
}

test();

```

Running this code throws a **`ReferenceError`**:

```text
ReferenceError: Cannot access 'x' before initialization

```

### Why this happens

1. **Hoisting of `let`:**
Variables declared with `let` and `const` are hoisted to the top of their block/function scope, but unlike `var`, they are **not initialized** with `undefined`.
2. **Shadowing:**
Because `let x` is declared inside `test()`, it shadows the outer `var x = 10` for that entire function scope. JavaScript will not look up to the outer scope for `x`.
3. **Temporal Dead Zone (TDZ):**
From the start of the function block until the line where `let x = 20` is evaluated, `x` exists in the **Temporal Dead Zone**. Any attempt to access `x` during this phase results in a `ReferenceError`.

### How to fix it

* **If you intended to log the inner variable**, initialize it before accessing it:

```javascript
function test() {
  let x = 20;
  console.log(x); // logs 20
}

```

* **If you intended to log the outer variable**, don't redeclare `x` inside the function:

```javascript
var x = 10;
function test() {
  console.log(x); // logs 10
}

```

### Scenario 2: Loops with Asynchronous Callbacks (`var` vs `let`)

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log("var:", i), 100);
}

for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log("let:", j), 100);
}

```

### Output

After approximately 100 milliseconds, the console will print:

```text
var: 3
var: 3
var: 3
let: 0
let: 1
let: 2

```

---

### Why this happens

**1. The `var` loop:**

* `var` is **function-scoped** (or globally scoped), not block-scoped.
* There is only **one shared instance** of `i` for all three iterations.
* The `setTimeout` callbacks are queued to run asynchronously on the event loop. By the time they execute 100ms later, the loop has finished and `i` has incremented to `3`.
* Each callback reads the same updated value: `3`.

**2. The `let` loop:**

* `let` is **block-scoped**.
* In a `for` loop, JavaScript creates a **new lexical binding** (a brand-new copy of `j`) for each iteration.
* Each `setTimeout` callback forms a closure over its own unique instance of `j` at that specific iteration (`0`, `1`, and `2`).

### Scenario 3: Redeclaration across Functions and Block Scopes

```javascript
var a = 1;

function foo() {
  if (true) {
    var a = 2;
    let b = 3;
  }
  console.log(a);
  console.log(typeof b);
}

foo();
console.log(a);

```

**Output:**

```text
2
"undefined"
1

```

The provided output is **accurate**. Here is the step-by-step breakdown of how JavaScript evaluates this code:

---

### Step-by-Step Execution

**1. `console.log(a)` inside `foo()**`

* Variables declared with `var` are **function-scoped**, not block-scoped.
* The declaration `var a = 2;` inside the `if (true)` block is hoisted to the top of `foo()`.
* Inside `foo()`, this local `a` shadows the outer global `var a = 1`.
* When `var a = 2` executes, the local `a` is set to `2`.
* Therefore, `console.log(a)` outputs **`2`**.

**2. `console.log(typeof b)` inside `foo()**`

* Variables declared with `let` are **block-scoped**.
* `b` exists only within the `{ ... }` curly braces of the `if` block.
* Outside that block, `b` is undeclared.
* Using the `typeof` operator on an undeclared variable is safe in JavaScript and does not throw a `ReferenceError`—it evaluates to the string **`"undefined"`**.

**3. `console.log(a)` outside `foo()**`

* The `var a = 2` inside `foo()` only affected the function's internal lexical environment.
* The outer global variable `var a = 1` remains untouched.
* Therefore, the final line outputs **`1`**.

### Scenario 4: Global Object Properties (`window` / `globalThis`)

```javascript
var x = "varX";
let y = "letY";
const z = "constZ";

console.log(this.x);
console.log(this.y);
console.log(this.z);

```

The output depends on the environment where the code runs:

---

### 1. In a Browser (Standard `<script>` / Global Scope)

```text
"varX"
undefined
undefined

```

* **`var`:** Declaring a variable with `var` in the global scope creates a property on the global object (`window`), so `this.x` evaluates to `"varX"`.
* **`let` and `const`:** These are block-scoped declarations stored in the top-level declarative environment record. They do **not** become properties on the global object, so `this.y` and `this.z` return `undefined`.

---

### 2. In Node.js (CommonJS Module)

```text
undefined
undefined
undefined

```

* In Node.js, each file is wrapped inside a module function. At the top level of a file, `this` refers to `module.exports` (which starts as an empty object `{}`), not `global`.
* None of `var`, `let`, or `const` attach properties to `module.exports`.

---

### 3. In ES Modules (`type="module"`)

```text
TypeError: Cannot read properties of undefined (reading 'x')

```

* In ECMAScript modules (both in browsers and Node.js), top-level `this` is explicitly `undefined`. Attempting to read `this.x` throws a `TypeError`.

### Scenario 5: Parameter Default Values & TDZ

```javascript
let x = 1;

function bar(x = x) {
  return x;
}

bar();

```

Running this code throws a **`ReferenceError`**:

```text
ReferenceError: Cannot access 'x' before initialization

```

---

### Why this happens

1. **Parameters have their own scope:**
When default parameter values are evaluated, they run in an intermediate scope between the outer scope and the function body.
2. **Self-referential default value:**
In `x = x`, the identifier `x` on the right-hand side refers to the parameter `x` itself, **not** the outer `let x = 1`.
3. **Temporal Dead Zone (TDZ):**
Function parameters behave like `let` bindings. While the default expression is being evaluated to initialize the parameter `x`, `x` is still inside its own **Temporal Dead Zone**. Trying to read `x` before its initialization is complete triggers a `ReferenceError`.

---

### How to get the outer variable

If the goal is to default to the outer variable `x`, use a different name for the parameter:

```javascript
let x = 1;

function bar(param = x) {
  return param;
}

console.log(bar()); // 1

```

### Scenario 6: `const` Mutability vs Object Freezing

```javascript
const obj = {
  a: 10,
  nested: { b: 20 }
};

obj.a = 30;
console.log(obj.a);

Object.freeze(obj);
obj.a = 40;
obj.nested.b = 50;

console.log(obj.a);
console.log(obj.nested.b);

```

```text
30
30
50

```

*(Note: In strict mode (`"use strict";`), the line `obj.a = 40;` will throw a `TypeError: Cannot assign to read only property 'a'` instead of failing silently).*

---

### Why this happens

* **`obj.a = 30;`**
Declaring an object with `const` prevents the variable identifier (`obj`) from being reassigned to a new reference, but it does **not** make the object's properties immutable. Mutating `obj.a` succeeds, logging `30`.
* **`Object.freeze(obj);` (Shallow Freeze)**
`Object.freeze` makes an object's direct properties read-only and non-configurable.
* Attempting to set `obj.a = 40` fails (it is ignored in non-strict mode, or throws in strict mode). Hence, `console.log(obj.a)` still outputs **`30`**.
* **Freezing is shallow:** It only freezes the immediate properties of `obj`. The nested object (`obj.nested`) remains a separate reference that is **not** frozen.
* Mutating `obj.nested.b = 50` succeeds, so `console.log(obj.nested.b)` outputs **`50`**.   ₹

### Scenario 7: `switch` Statement Scope Trap

```javascript
const action = "A";

switch (action) {
  case "A":
    let result = "Result A";
    console.log(result);
    break;
  case "B":
    let result = "Result B";
    console.log(result);
    break;
}

```

**Output:**
`SyntaxError: Identifier 'result' has already been declared`

**Explanation:**
A `switch` statement has **one single block scope** for all `case` clauses. Declaring `let result` in `case "A"` and `let result` in `case "B"` inside the same switch block attempts to re-declare a `let` variable in the same scope, causing a syntax error before execution.

*Fix:* Enclose `case` blocks in curly braces `{}` to create distinct block scopes:

```javascript
case "A": {
  let result = "Result A";
  break;
}

```

### Scenario 1: Function Hoisting vs. `var` vs. Block Scope Override

```javascript
var foo = 1;

function test() {
  console.log(foo);

  return;

  function foo() {
    return "hoisted";
  }
}

test();
console.log(typeof foo);

```

**Output:**

```text
[Function: foo]
number

```

**Explanation:**

1. **Inside `test()`:** Function declarations are hoisted **with their definition**, whereas `var` is hoisted as `undefined`. Function hoisting takes precedence. Therefore, inside `test()`, `foo` is initialized as the function `foo()` before any execution begins.
2. Even though `return` appears before the `function foo() {}` declaration in code order, hoisting occurs at compile time! Thus, `console.log(foo)` prints `[Function: foo]`.
3. **Outside `test()`:** The global variable `foo = 1` remains untouched by `test()`'s local function scope. `typeof foo` in the global scope outputs `"number"`.

---

### Scenario 2: Parameter Scope TDZ with Destructuring Defaults

```javascript
let a = 1;

function demo(
  a = a,
  b = () => a
) {
  let a = 2;
  console.log(b());
}

demo();

```

**Output:**
`ReferenceError: Cannot access 'a' before initialization`

**Explanation:**

1. When a function has default parameters, JavaScript creates an **intermediate Parameter Scope** that sits between the Global Scope and the Function Body Scope.
2. Parameter default evaluation executes sequentially: `a = a` evaluates `a` on the right-hand side to assign to parameter `a`. Because parameter `a` is defined in parameter scope using TDZ initialization rules, reading `a` before it finishes initializing throws a **`ReferenceError`**.
3. Note: The code never even reaches the function body (`let a = 2`), failing instantly during parameter binding.

### Scenario 3: Microtask Queue + Uncaught ReferenceError in TDZ

```javascript
console.log("Start");

setTimeout(() => console.log("Timeout"), 0);

Promise.resolve().then(() => {
  console.log("Promise 1");
  console.log(value); // TDZ Access
  let value = 100;
});

Promise.resolve().then(() => {
  console.log("Promise 2");
});

console.log("End");

```

**Output:**

```text
Start
End
Promise 1
Uncaught ReferenceError: Cannot access 'value' before initialization
Promise 2
Timeout

```

**Explanation:**

1. **Synchronous Phase:** Logs `"Start"` and `"End"`.
2. **Microtask Queue Processing:**

* **Promise 1 Callback:** Executes, logs `"Promise 1"`. Then attempts to access `value` before `let value = 100`. It throws an unhandled `ReferenceError`.
* **Promise 2 Callback:** Even though Promise 1 threw an unhandled error, microtask queue execution does **not** stop the Event Loop! Promise 2 was already enqueued, so it executes next and logs `"Promise 2"`.

1. **Macrotask Queue Processing:** `setTimeout` callback executes last, logging `"Timeout"`.

### Scenario 4: Class Fields Execution Order & Scope Shadowing

```javascript
var name = "Global";

class Person {
  name = "Instance";

  getName = () => {
    return this.name;
  };

  test() {
    var name = "Local";
    return (() => {
      return this.getName();
    })();
  }
}

const p = new Person();
const fn = p.test;

console.log(p.test());
console.log(fn());

```

**Output:**

```text
Instance
TypeError: Cannot read properties of undefined (or Cannot read property 'getName' of undefined)

```

**Explanation:**

1. `p.test()` runs with `this` bound to instance `p`. Inside `test()`, `this.getName()` resolves to the arrow function `getName`, which returns `this.name` (`"Instance"`). The local `var name = "Local"` inside `test()` does not affect `this.name`.
2. `fn()` stores a reference to `p.test` and calls it as a standalone function call.
3. Classes in JavaScript are **implicitly executed in Strict Mode** (`"use strict"`). In strict mode, standalone function invocations have `this = undefined` instead of `window`/`global`.
4. Therefore, inside `fn()`, trying to evaluate `this.getName()` throws a `TypeError: Cannot read properties of undefined`.

### Scenario 5: Variable Hoisting inside Block-Scoped `try/catch` and `IIFE`

```javascript
var res = [];

for (var i = 0; i < 3; i++) {
  (function () {
    try {
      throw i;
    } catch (i) {
      var i = 10;
      let j = 20;
      res.push(i);
    }
  })();
}

console.log(res);
console.log(typeof i);

```

**Output:**

```text
[10, 10, 10]
number

```

**Explanation:**

1. **Catch Clause Scope:** The parameter `catch (i)` creates a special block-scoped variable `i` that receives the thrown value (`0`, `1`, `2`).
2. **`var i = 10` inside `catch`:** `var` declarations do **not** respect `catch` block scopes! `var i` hoists up to the enclosing **IIFE function scope**.
3. However, inside the `catch` block, the name `i` refers to the `catch` parameter `i`. Assigning `i = 10` overwrites this local catch binding to `10`.
4. `res.push(i)` pushes `10` in all 3 iterations.
5. **Global `i`:** The loop variable `var i` in `for (var i = 0; i < 3; i++)` is in global scope. The IIFE hides the global `i` inside its body. After the loop terminates, global `i` equals `3`, so `typeof i` is `"number"`.

### Scenario 1: IIFE Parameter Shadowing vs. Outer Mutability

```javascript
var x = 10;
var y = 20;

(function (x) {
  console.log(x, y);
  var y = 30;
  x = 40;
  console.log(x, y);
})(x);

console.log(x, y);

```

**Output:**

```text
10 undefined
40 30
10 20

```

**Explanation:**

1. **First `console.log(x, y)`:**

* `x` is passed into the IIFE as an argument (`10`). The parameter `x` shadows the global `x`.
* Inside the IIFE, `var y = 30;` causes the declaration `var y` to be **hoisted** to the top of the IIFE function scope with initial value `undefined`. Thus, local `y` shadows global `y` before initialization, printing `10 undefined`.

1. **Second `console.log(x, y)`:** Local `y` is assigned `30`, and local `x` is re-assigned `40`. Prints `40 30`.
2. **Global `console.log(x, y)`:** Primitive values (`10`) are passed by value into functions. Mutating local `x` inside the IIFE did not affect global `x`. Furthermore, local `var y` was function-scoped to the IIFE. The outer variables remain `10 20`.

### Scenario 2: The classic "Module Pattern" Closure Leak

```javascript
const counter = (function () {
  var count = 0;

  return {
    inc: function () {
      return ++count;
    },
    get count() {
      return count;
    },
    reset: function () {
      count = 0;
    }
  };
})();

var getCount = counter.inc;

console.log(counter.inc());
console.log(getCount());
console.log(counter.count);

```

**Output:**

```text
1
2
2

```

**Explanation:**

1. **`counter.inc()`**: Calls `inc()`, which increments the closed-over variable `count` from `0` to `1` and returns `1`.
2. **`getCount()`**: Assigning `counter.inc` to `getCount` extracts the `inc` function reference. When invoked as `getCount()`, does it lose its `count` state? **No!** Closure is bound to **where the function was defined**, not where or how it is invoked. `getCount()` increments the same closed-over `count` to `2` and returns `2`.
3. **`counter.count`**: Reads the getter `get count()`, which accesses the shared `count` variable held in closure (`2`).

### Scenario 3: Named IIFE Self-Reference Edge Case

```javascript
var result = (function foo(flag) {
  foo = 100; // Attempting to overwrite named IIFE identifier

  if (flag) {
    return foo(false);
  }

  return typeof foo;
})(true);

console.log(result);

```

**Output:**

```text
"function"

```

**Explanation:**

1. In a **Named Function Expression** (like `(function foo() {})`), the identifier `foo` is bound **read-only** inside its own local scope so the function can reference itself recursively.
2. In non-strict mode, attempting to reassign `foo = 100` **fails silently** (in strict mode, it would throw a `TypeError`).
3. During the first call `foo(true)`: `foo = 100` is ignored. It enters `if (flag)` and makes a recursive call `foo(false)`.
4. During the recursive call `foo(false)`: `flag` is `false`. It returns `typeof foo`. Because `foo` is still the function itself, `typeof foo` evaluates to `"function"`.

### Scenario 4: Shared Closures in Object Generators via IIFE

```javascript
var createHandlers = (function () {
  var id = 0;

  return function () {
    id++;
    return {
      getId: () => id,
      nextId: function () {
        return ++id;
      }
    };
  };
})();

const h1 = createHandlers();
const h2 = createHandlers();

console.log(h1.getId());
console.log(h2.getId());
console.log(h1.nextId());
console.log(h2.getId());

```

**Output:**

```text
1
2
3
3

```

**Explanation:**

1. The outer IIFE executes **once** and creates a **single shared closure context** containing `var id = 0`.
2. `createHandlers` holds a reference to the returned inner function.
3. **`const h1 = createHandlers()`**: `id` increments to `1`. `h1` receives object methods closing over `id`. `h1.getId()` returns `1`.
4. **`const h2 = createHandlers()`**: `createHandlers()` is called a second time, incrementing the **same shared `id**` to `2`. `h2.getId()` returns `2`.
5. **`h1.nextId()`**: `h1` calls `nextId()`, which increments the shared `id` to `3` and returns `3`.
6. **`h2.getId()`**: Since `h1` and `h2` share the exact same `id` variable through the outer IIFE's closure, `h2.getId()` now reads `3`.

### Scenario 5: Double IIFE Trap with `this` and Arrow Functions

```javascript
var name = "Global";

const obj = {
  name: "Object",
  method: function () {
    return (function () {
      return () => {
        return this.name;
      };
    })()();
  }
};

console.log(obj.method());

```

**Output (in Browser non-strict mode):**

```text
"Global"

```

*(Note: In strict mode or Node.js module top-level, this would result in a `TypeError: Cannot read properties of undefined` or `undefined`)*

**Explanation:**

1. `obj.method()` is invoked as a method on `obj`, so inside `method`, `this` points to `obj`.
2. Inside `method`, an **IIFE** `(function() { ... })()` is immediately executed as a standalone function call.
3. Standalone function invocations set `this` to `window`/`global` (or `undefined` in strict mode). Thus, inside the inner IIFE, `this` is `window`.
4. The inner IIFE returns an **arrow function** `() => this.name`. Arrow functions capture `this` lexically from their immediate enclosing scope (the IIFE).
5. The final `()` executes the returned arrow function, which reads `this.name` from the IIFE's context (`window.name`), logging `"Global"`.
