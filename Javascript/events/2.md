**1. `e.target` vs. `e.currentTarget` in Event Bubbling**

| Property              | Definition                                                           | Value During Bubbling                                                          | Example                                                   |
| --------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------- |
| **`e.target`**        | The innermost DOM element where the event was physically dispatched. | **Stays constant** as the event bubbles up the DOM tree.                       | The specific `<span>` or `<button>` clicked by the user.  |
| **`e.currentTarget`** | The DOM element to which the event listener is currently attached.   | **Changes dynamically** to reference whichever element's handler is executing. | The parent `<ul>` or `<div>` that has `addEventListener`. |

```javascript
// HTML: <div id="parent"><button id="child">Click Me</button></div>

document.getElementById('parent').addEventListener('click', (e) => {
  console.log(e.target.id);        // "child" (where the click originated)
  console.log(e.currentTarget.id); // "parent" (where the listener is attached)
});

```

**2. `event.stopPropagation()` vs. `event.stopImmediatePropagation()**`

Both methods halt event flow, but they differ in how they handle other listeners on the **same** DOM element:

* **`event.stopPropagation()`:**
* Stops the event from traveling further up (bubbling) or down (capturing) the DOM tree.
* **Does NOT stop** other listeners attached to the *exact same element* from executing.

* **`event.stopImmediatePropagation()`:**
* Stops the event from traveling up or down the DOM tree.
* **Additionally halts** all remaining listeners attached to the *same element* for that event type.

```javascript
const btn = document.querySelector('#btn');

btn.addEventListener('click', (e) => {
  e.stopImmediatePropagation();
  console.log('Handler 1 runs');
});

btn.addEventListener('click', () => {
  // Never runs because Handler 1 called stopImmediatePropagation()
  console.log('Handler 2 runs');
});

```

> **Note on `preventDefault()`:** Neither propagation method prevents default browser behavior (such as checkbox toggling or form submission). To halt default browser behavior, call `event.preventDefault()`.

**3. React Synthetic Events & Event Delegation**

React wraps native browser events in a cross-browser wrapper called **`SyntheticEvent`**. It normalizes event properties across browsers while maintaining the same interface as the W3C spec (`stopPropagation()`, `preventDefault()`, etc.).

**How React Implements Event Delegation:**

* **Root-Level Attachment:** React does not attach inline event listeners to individual DOM nodes. Instead, it attaches a single native listener per event type to the **root container** (the DOM node passed to `createRoot`, e.g., `<div id="root"></div>`).
* **Synthetic Event Dispatch:**

1. When a native event bubbles up to the root container, React captures it.
2. React constructs a `SyntheticEvent` instance.
3. React inspects the internal fiber tree to determine the component hierarchy from the origin element up to the root.
4. It dispatches the synthetic event through that component tree, simulating capturing and bubbling phases in virtual space.

* **No More Event Pooling:** In modern React (React 17+), synthetic events are **not pooled**. Event objects are not cleared between ticks, so accessing `e.target` inside asynchronous callbacks (e.g., `setTimeout` or `await`) works without needing `e.persist()`.
* **Micro-Frontend Isolation:** Because delegation occurs at the container root rather than `document`, multiple independent React roots on the same page do not leak or intercept each other's delegated events.
