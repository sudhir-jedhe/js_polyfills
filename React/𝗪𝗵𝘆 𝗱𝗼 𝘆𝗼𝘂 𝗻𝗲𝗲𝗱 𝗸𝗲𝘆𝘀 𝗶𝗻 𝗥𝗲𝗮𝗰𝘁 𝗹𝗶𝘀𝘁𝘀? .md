React needs keys to **uniquely identify list items** so its reconciliation algorithm knows which elements to insert, keep, move, or remove when the list changes.

Without keys, React falls back to matching elements by their **index position in the DOM tree**.

---

**1. Efficient DOM Reconciliation (Performance)**

When an item is added to the beginning of an unkeyed list, React cannot tell that existing items were just shifted down:

* **Without keys:** React mutates every single existing DOM node to match the shifted data and appends one at the end ($O(N)$ updates).
* **With stable keys:** React realizes existing items only changed positions, moves the existing DOM nodes, and inserts just one new DOM node ($O(1)$ update).

---

**2. Preserving Component and DOM State**

Keys tie internal state (like user inputs, scroll positions, or local `useState`) to the specific data item rather than its visual slot.

* **Without keys (or using index as key):** If you delete the first item in a list of form inputs, the new first item inherits the deleted item's input text and focus state.
* **With stable keys:** React destroys the removed item's state and cleanly preserves the state of the remaining items.

---

**Key Comparison**

| Approach                               | Insertion/Reorder Result                    | State Preservation                               |
| -------------------------------------- | ------------------------------------------- | ------------------------------------------------ |
| **No key / Array Index**               | Re-renders and mutates all subsequent nodes | Buggy; input/focus state bleeds into wrong items |
| **Unique Stable ID (e.g., `item.id`)** | Only reorders/inserts affected DOM nodes    | Correct; state stays attached to the data item   |

```jsx
// ❌ Anti-pattern: Missing key or array index
{items.map((item, index) => <ListItem key={index} data={item} />)}

// ✅ Best practice: Unique, persistent identifier from data
{items.map((item) => <ListItem key={item.id} data={item} />)}
