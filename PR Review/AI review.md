A structured checklist for evaluating and reviewing code generated by AI assistants (e.g., GitHub Copilot, ChatGPT, Claude, Cursor) before merging.

---

### 1. Hallucination & API Accuracy

* **Package & Dependency Verification:** Are all imported third-party libraries real, maintained, and actively in the project’s `package.json`, rather than fabricated "hallucinated" package names?
* **API Signature & Version Drift:** Does the code call real methods matching the project's installed package versions (e.g., avoiding deprecated v4 APIs when on v5, or inventing non-existent utility methods)?
* **Internal Function Signatures:** Does the AI accurately pass parameters and match the signatures of existing internal helpers and services within your repo?

---

### 2. Context Completeness & Logic Gaps

* **Edge Case Handling:** Has the AI omitted boundary cases (e.g., empty arrays `[]`, `null`/`undefined` payloads, `0` values, network timeouts, or non-200 responses) in favor of the "happy path"?
* **Subtle Arithmetic & Logic Flaws:** Are off-by-one errors ($<=$ vs $<$), inverted boolean checks, and timezone/date math explicitly verified?
* **Concurrency & Race Conditions:** If the AI added asynchronous operations, are requests cancellation-safe, properly awaited, and free of race conditions?

---

### 3. Security, Privacy & Compliance

* **Secret & Key Leakage:** Did the AI insert placeholder API keys, hardcoded credentials, or insecure fallback secrets instead of using environment variables?
* **Injection Vulnerabilities:** Are SQL queries, raw HTML injections (`dangerouslySetInnerHTML`), or shell executions parameterized and sanitized against XSS, SQLi, and command injection?
* **Insecure Defaults:** Did the generated code lower security standards (e.g., `CORS: *`, disabled SSL validation, or overly permissive auth rules) just to "make it work"?
* **Data Leakage in Logging:** Are sensitive user parameters (passwords, tokens, PII) avoided in auto-generated debug logging statements?

---

### 4. Code Quality & Architectural Consistency

* **Duplicate Utility Creation:** Did the AI write a custom helper function for something already available in your project's shared utilities (e.g., date formatting, currency parsing)?
* **Idiomatic Patterns:** Does the generated code adhere to your team's conventions (e.g., functional components with hooks vs. classes, preferred state libraries, custom error classes)?
* **Dead & Redundant Code:** Has the AI generated unnecessary boilerplate, unused variable declarations, or verbose nested conditionals that could be simplified?

---

### 5. Automated Testing & Verification

* **Asserting Reality vs. Mocking Everything:** Do the AI-generated unit tests actually execute meaningful assertions, or did it over-mock implementations to the point where tests pass unconditionally?
* **Negative Test Cases:** Did the AI generate test cases for unexpected inputs, network errors, and rejection scenarios, or only for the successful execution path?

A specialized checklist for drafting, reviewing, and validating **Skills and Tools** for Anthropic Claude (Claude API, Claude Desktop, and Agentic Workflows).

---

### 1. Schema Design & Parameter Typing

* **Strict JSON Schema Compliance:** Are all properties defined using valid JSON Schema types (`string`, `number`, `integer`, `boolean`, `array`, `object`)?
* **Explicit `required` Array:** Is every mandatory parameter explicitly listed in the `required` array, and are optional fields clearly documented?
* **Enums & Constrained Values:** Are parameters with fixed options constrained using `enum` (e.g., `["asc", "desc"]` or `["daily", "weekly"]`) rather than open strings?
* **Descriptive Property Metadata:** Does every parameter contain a concise `description` field explaining its purpose, expected format (e.g., `YYYY-MM-DD`, ISO-8601), and default behavior?

---

### 2. Prompt Engineering for Tool Descriptions

* **Clear Action Intent:** Does the root `description` state *what* the tool does, *when* Claude should invoke it, and *when it should avoid* invoking it?
* **Edge Case Instructions:** Are fallback guidelines included in the description (e.g., "If the user does not specify a city, default to the user profile city")?
* **Differentiating Overlapping Tools:** If multiple tools exist in the workspace (e.g., `search_users` vs `get_user_details`), does the description explicitly distinguish between them to prevent model confusion?
* **No Ambiguous Verbs:** Are vague terms like `process_data` or `do_action` replaced with precise semantic names like `fetch_sales_report` or `archive_slack_channel`?

---

### 3. Execution Safety & Sandboxing

* **Idempotency & Read vs. Write:** Are state-mutating tools (e.g., `delete_database_row`, `charge_credit_card`) marked with explicit human-in-the-loop (HITL) confirmation or guarded behind dry-run parameters (`dry_run: boolean`)?
* **Input Sanitization & Injection Defense:** Does the backend implementation sanitize arguments against SQL injection, path traversal (e.g., `../../etc/passwd`), and command injection before execution?
* **Least Privilege Access:** Are tool API keys and credentials scoped exclusively to the minimal permissions required for that single tool?

---

### 4. Error Handling & Feedback Loops

* **Actionable Error Responses:** When a tool fails on the backend, does it return structured, actionable error strings (e.g., `{"error": "User ID not found. Available IDs: [101, 102]"}`) so Claude can self-correct?
* **Graceful Timeouts:** Are long-running tool executions guarded with timeouts (e.g., 10–30 seconds) to prevent the agent from hanging indefinitely?
* **No Raw Stack Traces:** Are raw database crashes and unhandled system traces caught and transformed into clear semantic messages before being sent back to the model?

---

### 5. Output Optimization & Token Efficiency

* **Compact Output Payloads:** Does the tool return clean, structured JSON or Markdown, stripping unnecessary internal metadata, large binary blobs, and verbose logs to conserve Claude's context window?
* **Pagination for Large Results:** Do search or list tools implement limit/offset or cursor pagination (e.g., returning the top 5–10 results with a `has_more: true` flag)?
