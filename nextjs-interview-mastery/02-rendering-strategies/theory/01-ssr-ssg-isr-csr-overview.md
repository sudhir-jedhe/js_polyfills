# SSR, SSG, ISR, and CSR: The Four Rendering Strategies

Next.js supports four conceptually distinct ways to get HTML in front of a user, and picking the right one per route is one of the most consequential architectural decisions you'll make. All four still exist under the App Router, but the *mechanism* for choosing them has shifted from explicit exported functions (Pages Router) to implicit rendering behavior based on what your Server Components do (App Router).

**SSG (Static Site Generation)** — HTML is generated once, at **build time**, and served identically to every visitor from a CDN edge cache until the next deploy. Fastest possible response (no server work per request), cheapest to host, but the content is frozen until you rebuild. In the App Router, a route is statically generated by default *as long as* nothing in it opts into dynamic behavior.

```tsx
// app/blog/[slug]/page.tsx — statically generated per slug at build time
export async function generateStaticParams() {
  const posts = await getAllPostSlugs()
  return posts.map((slug) => ({ slug }))
}

export default async function BlogPost({ params }: { params: { slug: string } }) {
  const post = await getPost(params.slug) // fetch() defaults to cached, force-cache
  return <article>{post.body}</article>
}
```

**SSR (Server-Side Rendering)** — HTML is generated **fresh on every request**, on the server. Necessary for content that must reflect the exact current moment (per-user personalization, request-specific headers/cookies, data too volatile to cache). Costs a server round-trip per request — slower than SSG, but always current.

```tsx
// app/account/page.tsx — forced dynamic because it reads cookies per-request
import { cookies } from 'next/headers'

export default async function AccountPage() {
  const session = cookies().get('session')?.value
  const user = await getUserBySession(session)
  return <p>Welcome back, {user.name}</p>
}
```

**ISR (Incremental Static Regeneration)** — the hybrid: pages are statically generated like SSG, but Next.js will regenerate them in the background after a configured `revalidate` interval elapses, without requiring a full redeploy. Visitors keep getting the fast cached version while regeneration happens behind the scenes (stale-while-revalidate-ish); the *next* eligible request after regeneration completes gets the fresh version.

```tsx
// app/products/[id]/page.tsx — ISR, revalidate every 60 seconds
export const revalidate = 60

export default async function ProductPage({ params }: { params: { id: string } }) {
  const product = await getProduct(params.id)
  return <ProductDetails product={product} />
}
```

**CSR (Client-Side Rendering)** — the server sends minimal HTML (or none, for the specific content), and a Client Component fetches and renders data in the browser after hydration, typically via `useEffect`/`useState` or a data library like SWR/React Query. Still fully valid in the App Router for content that's genuinely user-specific, doesn't need SEO, or updates too frequently/interactively for server rendering to help — dashboards with live client-side polling, in-page search/filter UIs, or anything gated behind client-only browser APIs.

```tsx
'use client'
import { useEffect, useState } from 'react'

export function LiveNotifications() {
  const [notifications, setNotifications] = useState([])
  useEffect(() => {
    const id = setInterval(async () => {
      const res = await fetch('/api/notifications')
      setNotifications(await res.json())
    }, 5000)
    return () => clearInterval(id)
  }, [])
  return <ul>{notifications.map((n) => <li key={n.id}>{n.text}</li>)}</ul>
}
```

The decision isn't binary per app — it's per route, and often per component within a route (a mostly-static page can have one small CSR island, or a mostly-SSR page can render one ISR-cached subsection).
