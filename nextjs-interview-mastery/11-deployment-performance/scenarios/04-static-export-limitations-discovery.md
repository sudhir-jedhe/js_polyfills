# Scenario: A team hits static export's limits mid-project

**Problem:** A marketing team chose `output: 'export'` for their site early on, deploying to a low-cost static host (S3 + CloudFront) since the entire site was genuinely static content (landing pages, a pricing page, a blog built from Markdown at build time). Six months later, product wants to add: (1) a "request a demo" form that emails the sales team, and (2) a personalized "resume where you left off" banner on the blog for returning visitors based on a cookie. Both features are blocked, and the team isn't sure why — locally, everything "just works" in `next dev`.

**Approach:** Explain precisely why `next dev` masks the limitation (dev mode always runs a full Next.js server regardless of the `output: 'export'` config — the constraint only bites at `next build`/deploy time, once the static-only output is actually generated and served without a server), then evaluate the two features against static export's hard constraints individually rather than treating "add dynamic features" as one monolithic migration.

**Feature 1 (contact form backend):** A form submission handler is inherently a server-side concern — there's no Route Handler support in static export at all. Two viable paths: either deploy a small separate serverless function (outside the Next.js static export, e.g., a standalone AWS Lambda or a Cloudflare Worker) that the static site's client-side JS calls via `fetch`, or use a third-party form backend service (Formspree, Netlify Forms-equivalent) that doesn't require any Next.js server involvement at all. Neither requires abandoning static export for the rest of the site.

**Feature 2 (cookie-based personalized banner):** Reading a cookie to personalize content server-side is exactly the kind of request-time computation static export can't do (no `cookies()` at build time). But this feature doesn't strictly need a *server* to read the cookie — `document.cookie` is readable client-side. The fix is rendering the banner client-side: ship a static shell with no banner, and a small Client Component reads the cookie via `useEffect` and conditionally renders the banner after mount. This trades a "flash of no-banner" on first paint for keeping the rest of the site static.

**Outcome:** Both features are achievable without migrating off static export, because neither one strictly requires *server-side* dynamic rendering — they require *some* dynamic behavior, which client-side JS or an external service can provide. This is the deeper lesson to draw out: "static export can't do X" often specifically means "can't do X **on the server**, at build time," and plenty of dynamic-feeling features can still be layered on top of a static shell via client-side code or external services, without needing to abandon the cost and simplicity benefits of static hosting for the 95% of the site that genuinely is static.
